## 2. 产品定位

AI 商品决策助手是一款面向电商用户的智能导购工具。用户可以用自然语言描述真实购买需求，系统基于商品属性、价格、库存、销量、评分、评价内容、优惠信息和售后风险，输出可解释的商品推荐、商品对比、买前避坑和多轮追问建议。

一句话定位：

> 帮用户把“我该买哪个”变成一个可解释、可比较、可行动的购买决策。

## 3. 背景与机会

### 3.1 用户问题

在 C 端电商场景中，搜索和推荐已经能解决“找到商品”的问题，但还没有很好解决“买哪个更适合我”的问题。尤其在家电、数码、母婴、家居、厨房小电器等中高决策成本品类中，用户通常会遇到以下问题：

1. 商品信息过载，详情页参数多、评论多、活动多，用户难以快速判断重点。
2. 传统搜索依赖关键词，难以理解“租房两人用”“给老人用”“不要太吵”“小户型不占地方”等场景化需求。
3. 商品对比成本高，用户需要在多个商品详情页、评论区、攻略内容之间反复切换。
4. 平台推荐缺少解释，用户难以判断推荐结果是“真的适合我”还是“平台想卖这个”。
5. 买错商品后的退货、换货和售后成本高，影响用户体验和平台履约成本。

### 3.2 市场与业务机会

AI 导购具备明确的实际价值，但用户信任需要通过“可解释、可验证、少打扰”的体验建立。公开行业资料显示，消费者对 AI shopping assistant 的认知正在提升，但仍需要更强的信任感和实际帮助；同时，NRF 2025 年退货报告预计 2025 年线上销售退货率为 19.3%，买前决策质量对转化和售后成本都有直接影响。Grand View Research 也预计全球 AI shopping assistant 市场将从 2024 年的 34 亿美元增长到 2033 年的 285 亿美元，说明智能导购存在明确增长空间。

本产品的机会点不是单纯做一个聊天机器人，而是将自然语言理解、商品结构化数据、评价摘要、向量检索、全文检索和推荐解释结合起来，形成一个“买前决策辅助系统”。

## 4. 产品目标

### 4.1 用户目标

1. 用户可以用自然语言表达需求，不需要先理解复杂商品参数。
2. 用户可以快速获得 3-5 个可信商品推荐。
3. 用户可以看到推荐理由、风险提示、适合人群和不适合情况。
4. 用户可以通过多轮追问继续收窄条件。
5. 用户可以在一个页面完成商品理解、比较和决策。

### 4.2 业务目标

1. 提升从搜索/导购入口到商品点击的转化率。
2. 提升推荐商品加购率。
3. 降低用户决策时长。
4. 降低因“不符合预期”导致的退货率。
5. 沉淀用户真实需求表达，反哺商品运营、搜索和推荐策略。

### 4.3 技术目标

1. 复用当前项目的 LangGraph 工作流能力，完成可观测、可扩展的 AI 导购链路。
2. 复用 Qdrant 和 Elasticsearch，分别支撑商品语义召回和评价/属性全文检索。
3. 复用 FastAPI SSE 能力，实现逐步流式反馈。
4. 将 SQL 查询能力从“商家问数”调整为“用户商品决策数据查询”。

## 5. 目标用户

### 5.1 核心用户

| 用户类型 | 特征 | 核心诉求 |
| --- | --- | --- |
| 新手购买用户 | 对品类不了解，例如首次买空气炸锅、儿童安全座椅、扫地机器人 | 想知道怎么选、避开什么坑 |
| 场景型用户 | 有明确使用场景，例如租房、送礼、育儿、装修、养宠 | 希望系统按场景推荐，而不是按关键词搜索 |
| 对比纠结用户 | 已经收藏多个商品，但无法判断哪个更适合 | 希望快速比较优缺点 |
| 价格敏感用户 | 有预算上限，希望找到性价比高的商品 | 希望在预算内获得最优选择 |
| 低耐心用户 | 不愿意读长详情和大量评论 | 希望系统直接给结论和依据 |

### 5.2 首期品类建议

一期建议聚焦以下品类：

1. 厨房小电器：空气炸锅、电饭煲、咖啡机、破壁机。
2. 家居生活：收纳柜、人体工学椅、床垫、除湿机。
3. 数码配件：耳机、充电宝、键盘、显示器。
4. 母婴用品：安全座椅、婴儿推车、恒温壶。

一期不建议覆盖：

1. 服饰全品类：尺码、版型和审美偏好过于主观，退货影响因素复杂。
2. 美妆功效类：容易涉及功效承诺、敏感肌风险和合规边界。
3. 医疗健康类：风险高，需要更强合规审核。
4. 大家电安装类全流程：涉及安装、配送、上门服务和区域履约。

## 6. 核心场景

### 6.1 场景一：用户有需求但不会选参数

用户输入：

> 我想买一个适合两个人租房用的空气炸锅，预算 300 以内，主要做鸡翅和薯条，别太难洗。

系统输出：

1. 推荐 3 个空气炸锅。
2. 解释容量、功率、内胆材质、清洗难度和价格匹配情况。
3. 提示不建议购买容量过小或不可拆洗的型号。
4. 给出“最推荐”“预算优先”“清洗省心”三个角度的结论。

### 6.2 场景二：用户在多个商品之间纠结

用户输入：

> 帮我比较 A、B、C 三款筋膜枪，哪个更适合久坐上班族？

系统输出：

1. 对比重量、力度档位、噪音、续航、握持舒适度、差评关键词。
2. 标注每款商品的适合人群和风险点。
3. 给出明确结论：最适合久坐上班族的是哪一款。

### 6.3 场景三：预算约束下找最优解

用户输入：

> 500 元以内，送女朋友生日礼物，有质感一点，不要太普通。

系统输出：

1. 先追问年龄、关系阶段和兴趣偏好。
2. 如果用户跳过追问，系统按默认假设生成方案。
3. 推荐单品或礼物组合，并解释“为什么适合送礼”。

### 6.4 场景四：买前避坑

用户输入：

> 这款扫地机器人值得买吗？差评主要说什么？

系统输出：

1. 总结差评高频点。
2. 标注地图、避障、噪音、缠头发、耗材价格等风险。
3. 结合价格、竞品和用户场景给出是否值得买的判断。

### 6.5 场景五：多轮追问继续筛选

用户输入：

> 有没有更便宜的？

系统需要理解上一轮上下文，并在原品类、原使用场景下重新推荐更低价候选，不要求用户重新输入完整需求。

## 7. 功能范围

### 7.1 一期 MVP 范围

| 模块 | 功能 | 是否一期 |
| --- | --- | --- |
| 自然语言输入 | 用户输入购买需求、商品比较、避坑问题 | 是 |
| 意图识别 | 识别推荐、对比、评价摘要、追问、筛选条件修改 | 是 |
| 槽位抽取 | 抽取品类、预算、场景、人群、品牌、偏好、排除项 | 是 |
| 智能追问 | 信息不足时最多追问 1-2 个关键问题 | 是 |
| 商品召回 | 基于商品标题、类目、属性、评价关键词召回候选商品 | 是 |
| 商品重排 | 综合需求匹配、价格、评分、销量、评价风险、库存排序 | 是 |
| 推荐解释 | 输出推荐理由、适合人群、不适合情况、风险提示 | 是 |
| 商品对比 | 以表格展示候选商品核心差异 | 是 |
| SSE 流式反馈 | 展示理解需求、召回商品、分析评价、生成推荐等步骤 | 是 |
| 结果反馈 | 用户反馈推荐是否有帮助 | 是 |

### 7.2 二期范围

1. 价格监控与降价提醒。
2. 用户偏好记忆。
3. 图文评价摘要。
4. 搭配购买方案。
5. 购物车和优惠券计算。
6. 用户已购商品结合推荐。

### 7.3 暂不做范围

1. 跨平台比价。
2. 自动下单。
3. 强医疗、强金融、强法律属性商品推荐。
4. 完全个性化首页推荐流。
5. 商家广告投放排序后台。

## 8. 用户流程

### 8.1 首次推荐流程

```text
进入 AI 导购入口
  -> 输入自然语言需求
  -> 系统识别意图和槽位
  -> 判断信息是否足够
  -> 不足则追问关键问题
  -> 召回候选商品
  -> 分析商品属性和评价
  -> 重排候选商品
  -> 生成推荐结果
  -> 用户点击商品 / 继续追问 / 反馈
```

### 8.2 商品对比流程

```text
用户选择多个商品或输入商品名称
  -> 系统识别对比维度
  -> 拉取商品属性、价格、评价、售后数据
  -> 生成对比表
  -> 输出适合用户场景的购买建议
```

### 8.3 买前避坑流程

```text
用户输入目标商品
  -> 系统检索评论和售后数据
  -> 提取高频正向与负向反馈
  -> 判断风险是否与用户场景相关
  -> 输出是否值得购买和替代建议
```

## 9. 页面设计

### 9.1 AI 导购首页

核心组件：

1. 自然语言输入框。
2. 场景快捷入口：租房好物、送礼、母婴、厨房小电器、数码配件、家居收纳。
3. 历史咨询记录。
4. 热门问题推荐。

页面目标：

1. 降低用户提问门槛。
2. 引导用户表达场景，而不是只输入商品名。
3. 让用户知道这个能力可以解决推荐、对比和避坑问题。

### 9.2 对话推荐页

核心组件：

1. 用户问题气泡。
2. 系统追问气泡。
3. 推荐商品卡片。
4. 推荐理由。
5. 风险提示。
6. 商品对比表。
7. 继续追问输入框。
8. 有帮助 / 不准确反馈入口。

页面目标：

1. 让推荐过程可感知。
2. 让推荐结论可解释。
3. 让用户可以继续收窄条件。

### 9.3 商品对比页

核心字段：

| 字段 | 说明 |
| --- | --- |
| 商品名称 | 商品标题和主图 |
| 到手价 | 优惠后的预估价格 |
| 核心参数 | 品类相关关键参数 |
| 需求匹配度 | 与用户需求的匹配评分 |
| 评分与销量 | 平台评分、近 30 天销量 |
| 好评关键词 | 高频正向评价摘要 |
| 差评关键词 | 高频负向评价摘要 |
| 适合人群 | 系统推断的适合场景 |
| 不适合情况 | 明确提示用户避坑 |
| 推荐结论 | 推荐、备选、不建议 |

### 9.4 反馈组件

反馈选项：

1. 推荐准确。
2. 价格不合适。
3. 商品太少。
4. 理由不可信。
5. 没理解我的需求。
6. 商品已经无货。

反馈用途：

1. 优化召回和排序策略。
2. 识别模型理解失败案例。
3. 发现商品数据缺失问题。

## 10. 功能需求

### 10.1 自然语言理解

系统需要从用户输入中识别：

| 字段 | 示例 | 是否必需 |
| --- | --- | --- |
| 意图 | 推荐商品、比较商品、总结评价、继续筛选 | 是 |
| 品类 | 空气炸锅、安全座椅、耳机、床垫 | 是 |
| 预算 | 300 元以内、1000-1500 元 | 否 |
| 使用人群 | 老人、儿童、学生、上班族 | 否 |
| 使用场景 | 租房、小户型、送礼、通勤、旅行 | 否 |
| 偏好 | 静音、好清洗、轻便、颜值高 | 否 |
| 排除条件 | 不要白色、不要太重、不要某品牌 | 否 |
| 商品范围 | 指定商品、收藏商品、搜索结果商品 | 否 |

验收标准：

1. 对常见购买需求能够正确识别品类和意图。
2. 对预算、场景、人群、偏好等槽位的抽取准确率在测试集达到 85% 以上。
3. 对无法识别的品类需要返回友好提示，而不是强行推荐。

### 10.2 智能追问

触发条件：

1. 用户需求缺少品类。
2. 品类存在强关键参数，但用户未提供。
3. 用户需求过宽，候选商品过多。
4. 用户需求存在冲突，例如“越便宜越好，但必须旗舰款”。

追问规则：

1. 最多连续追问 2 次。
2. 每次只问 1 个最关键问题。
3. 提供快捷选项。
4. 用户可以跳过。
5. 用户回答“不知道”时，系统使用默认假设并说明。

示例：

```text
用户：想买安全座椅，预算 1500。
系统：主要给多大的孩子使用？
选项：0-1 岁 / 1-4 岁 / 4-12 岁 / 还不确定
```

### 10.3 商品召回

召回数据源：

1. 商品标题。
2. 商品类目。
3. 商品属性。
4. 商品详情文本。
5. 用户评价。
6. 历史购买和点击数据。

召回方式：

1. 关键词召回。
2. 向量召回。
3. 属性过滤。
4. 评价关键词召回。
5. 热销商品补召回。

召回要求：

1. 硬性条件必须优先过滤，例如预算、库存、下架状态。
2. 场景化描述需要通过语义召回处理，例如“出租屋”“小户型”“送长辈”。
3. 召回不足时，需要提示用户放宽条件。

### 10.4 商品排序

排序因子：

| 因子 | 权重建议 | 说明 |
| --- | --- | --- |
| 需求匹配度 | 35% | 商品属性和用户需求的匹配程度 |
| 价格竞争力 | 20% | 是否符合预算、同类价格优势 |
| 评价质量 | 20% | 好评质量、差评风险、评价数量 |
| 销量与热度 | 10% | 销量、点击、加购等行为数据 |
| 售后风险 | 10% | 退货率、售后投诉、质量问题 |
| 平台策略 | 5% | 活动、库存、履约效率 |

排序要求：

1. 平台策略权重不得过高，避免损害用户信任。
2. 差评集中在安全、质量、售后严重问题的商品不得进入主推荐。
3. 价格超过预算 30% 以上的商品默认不展示。
4. 略超预算但优势明显的商品可以展示，但必须显式标记。

### 10.5 推荐结果生成

推荐结果结构：

| 字段 | 说明 |
| --- | --- |
| 推荐结论 | 最推荐、预算优先、品质优先、谨慎购买 |
| 商品列表 | 3-5 个候选商品 |
| 推荐理由 | 和用户需求强相关的理由 |
| 风险提示 | 评价和售后中暴露的潜在问题 |
| 适合人群 | 哪类用户适合买 |
| 不适合情况 | 哪类用户不建议买 |
| 对比表 | 候选商品关键维度对比 |
| 下一步建议 | 继续筛选或购买建议 |

推荐要求：

1. 推荐理由必须绑定具体属性、价格、评价或销量依据。
2. 不允许只输出“性价比高”“口碑好”等空泛描述。
3. 不允许虚构商品参数和用户评价。
4. 数据不足时必须提示“当前评价样本不足”或“商品参数缺失”。

### 10.6 商品对比

支持入口：

1. 用户从推荐结果中选择商品对比。
2. 用户直接输入多个商品名称。
3. 用户从收藏夹或购物车选择商品。

对比维度：

1. 价格。
2. 核心参数。
3. 用户需求匹配度。
4. 好评关键词。
5. 差评关键词。
6. 售后风险。
7. 适合人群。
8. 不适合情况。

验收标准：

1. 至少支持 3 个商品横向对比。
2. 对比表必须包含明确结论。
3. 如果商品分属不同品类，需要提示不适合直接比较。

### 10.7 评价摘要与避坑

系统需要提取：

1. 高频正向评价。
2. 高频负向评价。
3. 质量问题。
4. 尺寸/适配问题。
5. 噪音/气味/耐用性问题。
6. 物流和售后问题。

输出要求：

1. 不展示大段原始评论。
2. 不编造评价内容。
3. 评论数量不足时提示样本不足。
4. 对严重风险给出明确“不建议”提示。

### 10.8 多轮追问

支持表达：

1. 有没有更便宜的？
2. 只看自营。
3. 不要白色。
4. 给老人用哪个更简单？
5. 帮我比较前两个。
6. 有无平替？
7. 这个适合小户型吗？

上下文要求：

1. 继承上一轮品类、预算、场景和候选商品。
2. 用户新增条件后，需要重新过滤和排序。
3. 用户反悔或删除条件时，需要恢复上一轮可用上下文。

## 13. 非功能需求

### 13.1 性能

1. 首个 SSE 进度事件返回时间不超过 1 秒。
2. 有缓存命中时，完整推荐结果返回时间不超过 3 秒。
3. 无缓存时，首屏推荐结果返回时间目标不超过 8 秒。
4. 商品召回候选数量建议控制在 50-200 个。

### 13.2 稳定性

1. SSE 连接需要支持超时处理。
2. 查询失败时必须返回用户可理解的错误信息。
3. 外部检索服务异常时，允许降级到关键词搜索。
4. LLM 调用失败时，支持重试和友好失败。

### 13.3 安全与合规

1. 不向用户暴露 SQL、系统提示词、内部权重和调试堆栈。
2. 不展示用户敏感画像。
3. 个性化推荐需要允许用户关闭。
4. 不做绝对化功效承诺。
5. 涉及儿童、安全、健康类商品时，必须使用谨慎表达。

### 13.4 可观测性

需要记录：

1. 意图识别耗时。
2. 商品召回耗时。
3. 评价摘要耗时。
4. LLM 生成耗时。
5. 推荐结果点击率。
6. 用户反馈类型。
7. 错误类型和失败节点。

## 15. 验收标准

### 15.1 基础功能验收

1. 用户输入完整需求后，系统能够返回至少 3 个推荐商品。
2. 每个推荐商品必须包含推荐理由和风险提示。
3. 推荐结果必须包含明确结论。
4. 商品对比必须支持至少 3 个商品。
5. 多轮追问必须继承上一轮上下文。
6. 无结果时必须说明原因并给出放宽条件建议。

### 15.2 异常场景验收

1. 用户输入为空时，前端禁止提交。
2. 用户输入无法识别时，系统提示用户补充品类或场景。
3. 商品库存不足时，不进入主推荐。
4. 评论样本不足时，系统必须提示样本不足。
5. 检索服务异常时，系统降级或返回友好错误。
6. LLM 生成失败时，系统返回错误事件，不中断页面状态。

### 15.3 内容安全验收

1. 不输出内部 SQL。
2. 不输出系统提示词。
3. 不编造商品参数。
4. 不编造评价内容。
5. 不做绝对安全、绝对功效承诺。

## 17. 与当前项目的改造关系

当前 `shopkeeper-agent` 已经具备以下可复用能力：

1. FastAPI 后端入口。
2. SSE 流式返回。
3. LangGraph 节点编排。
4. Qdrant 向量召回。
5. Elasticsearch 全文检索。
6. MySQL 结构化查询。
7. React 前端对话界面。

建议改造方向：

| 当前能力 | 改造后用途 |
| --- | --- |
| 自然语言问数 | 自然语言购物需求理解 |
| 字段/指标召回 | 商品属性/评价/场景召回 |
| SQL 生成与执行 | 查询商品、价格、库存、评价、经营指标 |
| LangGraph 工作流 | 需求理解、追问、召回、排序、解释、反馈 |
| SSE 进度事件 | 展示 AI 导购执行过程 |
| 前端聊天界面 | C 端导购对话页 |

推荐的新工作流：

```text
extract_intent
  -> extract_slots
  -> decide_clarification
  -> recall_products
  -> analyze_reviews
  -> rank_products
  -> generate_recommendation
  -> render_comparison
  -> collect_feedback
```

## 18. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 用户不信任推荐 | 认为推荐是广告 | 推荐理由绑定真实属性、评价和价格依据 |
| 模型幻觉 | 编造商品参数或评价 | 所有关键事实从结构化数据和检索结果中取值 |
| 追问太多 | 用户流失 | 最多追问 2 次，允许跳过 |
| 推荐太泛 | 用户觉得没用 | 强化场景槽位和不适合情况 |
| 数据缺失 | 无法准确推荐 | 显示数据不足，并给出保守建议 |
| 延迟过高 | 用户等待焦虑 | SSE 展示进度，缓存高频问题 |
| 商业化干扰 | 推荐偏广告商品 | 限制平台策略权重，保留用户反馈入口 |

## 19. 后续迭代方向

1. 增加用户偏好记忆，例如品牌偏好、预算区间、避雷品牌。
2. 增加降价提醒和历史价格对比。
3. 增加图片识别，支持“按图找相似商品”。
4. 增加购物车组合优化，例如满减、凑单、优惠券计算。
5. 增加家庭场景长期助手，例如搬家清单、育儿采购清单、租房好物清单。
6. 将用户真实 query 聚类，反哺搜索词库、商品标签和运营专题。
